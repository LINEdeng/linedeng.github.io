## 1. 概念起源与定义

### 1.1 什么是 Vibe Coding

**Vibe Coding**（氛围编程）是一种由 **大语言模型（LLM）驱动**的全新编程风格，核心理念是：**你用自然语言描述意图，AI 负责编写代码，你负责审查结果、给反馈、推进方向。**

> "Fully give in to the vibes, embrace exponentials, and forget that the code even exists."  
> — Andrej Karpathy，2025 年 2 月

### 1.2 起源背景

| 时间 | 事件 |
|------|------|
| 2025 年 2 月 | Andrej Karpathy 在 X（前 Twitter）上首次提出"Vibe Coding"概念 |
| 2025 年 12 月 | Karpathy 个人实践转折点——模型生成的代码"直接能用，不再需要修正" |
| 2025 年 | Collins 词典将"Vibe Coding"选为 **2025 年度词汇** |
| 2026 年 | Vibe Coding 成为主流开发方法论，87% 的 Fortune 500 企业已采用 |

### 1.3 相关概念辨析

| 概念 | 定义 | 特点 |
|------|------|------|
| **传统编程** | 人亲手逐行编写代码 | 100% 人工掌控，速度慢但理解深 |
| **Copilot 辅助编程** | AI 提供代码补全建议，人保留完全审查权 | 工具属性，人始终是主角 |
| **Vibe Coding** | 人描述意图，AI 生成/修改/调试代码 | 人转为"意图设定者 + 结果审查者" |
| **Agentic Engineering** | AI Agent 自主规划和执行多步任务 | 最高自主级别，适合复杂长任务 |

> **重要区分**：Vibe Coding 抬高的是"下限"（让非开发者也能快速出成果），Agentic Engineering 抬高的是"上限"（让有经验的工程师处理更复杂的任务）。两者是互补关系，不是替代关系。

## 2. 核心哲学与思维方式

### 2.1 核心分工原则

```
你（人）→ 想清楚要做什么（方向、架构、技术决策）
AI → 帮你做（代码生成、测试、文档、重构）
```

**Vibe Coding 不是让 AI 替你思考，而是让 AI 替你执行。**

### 2.2 范式转变

| 维度 | 传统开发 | Vibe Coding |
|------|----------|-------------|
| **思考方式** | 先周密设计架构，再动手 | 边做边想，逐轮提示 |
| **编码方式** | 亲手逐行编写 | AI 自动生成 |
| **调试方式** | 深入分析，精确定位 | 反馈给 AI，循环修正 |
| **需求文档** | 给人看的交付物 | 人 + AI 共读的核心输入 |
| **流程结构** | 线性、有序 | 循环、交织 |
| **代码掌控** | 完全理解每行代码 | 关注结果，弱化细节（但不放弃审查） |
| **开发速度** | 稳健但较慢 | 快速迭代 |

### 2.3 适合与不适合的场景

#### ✅ 适合 Vibe Coding 的场景

- 原型验证与 MVP 快速构建
- 个人工具和内部脚本
- 前端 UI 快速迭代
- 文档、测试代码、配置文件的生成
- 有明确验收标准的可验证任务
- 重复性高的 CRUD 业务逻辑

#### ❌ 不适合 Vibe Coding 的场景

- 系统级架构设计决策（分布式、高可用、安全关键）
- 性能要求极高的底层算法
- 需要深度 Debug 和精确问题定位的场景
- 代码美学要求极高的核心库开发
- 长期维护的核心基础设施

#### ⚠️ Simon Willison 的警示

> "Vibe Coding 降低了写代码的门槛，却没有降低调试的门槛。"

## 3. 完整工作流程（步骤详解）

> **⚠️ 重要提醒**：第一步不是直接写代码，而是**先写 PRD 文档**。有结构化 PRD 的项目，MVP 完成率达 85%；没有的只有 22%。

### 完整工作流示意图

```
┌─────────────────────────────────────────────────────────┐
│                    宏观开发生命周期                        │
│                                                          │
│  ① 写 PRD 文档（SPACE 框架）                              │
│       ↓                                                  │
│  ② 建立项目上下文（CLAUDE.md / tech-stack.md）             │
│       ↓                                                  │
│  ③ 拆分任务 → 生成实施计划（implementation-plan.md）        │
│       ↓                                                  │
│  ④ AI 生成初始代码                                        │
│       ↓                                                  │
│  ┌─────────── 核心迭代循环（精髓） ───────────┐            │
│  │  运行测试 → 发现问题 → 反馈给 AI → 修改   │            │
│  └──────────────────────────────────────────┘            │
│       ↓（满足验收标准后退出循环）                          │
│  ⑤ 人工代码走查                                           │
│       ↓                                                  │
│  ⑥ 部署上线                                              │
└─────────────────────────────────────────────────────────┘
```

### 步骤一：撰写 PRD 文档（SPACE 框架）

这是 **Vibe Coding 最关键的第一步**，也是与传统开发最本质的区别。

PRD 文档的定位不是"给人看的交付物"，而是 **"高质量的长上下文 Prompt"**——让 AI 能够正确理解你的意图，稳定地产出符合预期的代码。

详细内容见第 4 节。

---

### 步骤二：建立项目上下文

在项目根目录创建以下文件，为 AI 提供持久化上下文：

| 文件 | 作用 |
|------|------|
| `CLAUDE.md` | 项目背景、技术栈、代码规范、架构决策 |
| `tech-stack.md` | 技术选型理由、依赖版本、环境要求 |
| `implementation-plan.md` | 分阶段实施计划（详见步骤三） |
| `memory-bank/` | 记忆库文件夹，包含上述所有文件 |
| `progress.md` | 记录已完成步骤 |
| `architecture.md` | 各文件作用说明 |

> **核心原则**：上下文文件越短越好，不写 AI 能从代码中直接读出的内容。每次启动对话时，AI 会自动加载这些上下文。

---

### 步骤三：拆分任务并生成实施计划

基于 PRD，生成详细的 **分步实施计划**（`implementation-plan.md`）：

**原则：**
- 每步必须小而具体（不超过 2-3 个文件/函数）
- 每步必须包含验证正确性的测试
- **严禁在计划中包含代码**——只写清晰、具体的指令
- 从 Phase 0（MVP 最小可行版本）开始，逐步扩展

**格式示例：**

```markdown
# 实施计划

## Phase 0：核心功能
### 步骤 1
- **任务**：创建数据库模型 `User` 和 `Post`
- **文件**：`src/models/`
- **验证**：运行 `npm test -- --grep "User model"`
- **约束**：遵循现有 Prisma schema 风格

### 步骤 2
- **任务**：实现 POST /users 注册接口
- **文件**：`src/routes/auth.ts`
- **依赖**：依赖步骤 1 完成的 User 模型
- **验证**：运行 `curl -X POST http://localhost:3000/api/users -d "{}"` 验证返回格式
```

---

### 步骤四：AI 生成代码

向 AI 提交实施计划中的第一步，用自然语言描述任务：

**好的 Prompt 示例：**

> "在 `src/routes/` 下创建用户注册接口 POST /register，使用 Prisma ORM 操作 `User` 模型，返回 JWT token。参考 `src/middleware/errorHandler.js` 的错误处理风格。"

**错误的 Prompt 示例：**

> "帮我写一个用户注册功能"

---

### 步骤五：运行测试

将 AI 生成的代码投入运行环境进行测试：

- 检查程序行为是否符合预期
- 验证边界条件和异常处理
- 观察性能表现
- AI 代码"自带事实校验"——运行即可暴露问题

---

### 步骤六：反馈迭代（核心循环）

这是 Vibe Coding 的精髓所在。将发现的问题以新的提示形式告诉 AI：

| 场景 | 反馈示例 |
|------|----------|
| 缺少错误处理 | "刚才的代码在文件不存在时会报错，请增加错误处理" |
| 运行时崩溃 | "程序提示空指针异常，请找出原因并修复" |
| 逻辑不对 | "结果不太对，请添加对空值的过滤" |
| 性能问题 | "这段代码在大数据量下性能差，请优化复杂度" |

AI 接收新指令后产出改进版本，返回步骤五再次运行。**循环迭代，直到满足验收标准。**

> **实用技巧**：如果同一个问题纠正超过 2 次仍不理想，使用 `/clear` 重置对话上下文，往往能获得更好的结果。

---

### 步骤七：人工代码走查

**⚠️ 这一步绝对不能跳过。** 即使 AI 写的代码能跑，也必须由人来 Review：

#### 必须人工审查的高风险场景

1. 涉及身份认证和授权的代码
2. 涉及支付、金融、医疗等安全关键领域
3. 处理用户敏感数据的逻辑
4. 涉及并发和锁机制的代码
5. 涉及系统级资源操作（文件、网络、系统调用）
6. 核心业务规则的实现逻辑

#### AI 辅助 Code Review

可以用 AI 审查 AI 生成的代码，但要**由人亲自审查**以下项目：

| 审查项 | 说明 |
|--------|------|
| 逻辑漏洞 | AI 可能"听起来对但实际错" |
| 安全问题 | SQL 注入、XSS、敏感信息泄露 |
| 业务理解偏差 | AI 可能误解了需求的真实意图 |
| 代码风格一致 | 是否符合团队规范 |

---

### 步骤八：部署上线

确认代码质量后，部署发布。建议先在隔离环境（沙箱）验证，再上生产。

## 4. SPACE PRD 框架：如何写好需求文档

### 4.1 框架概述

**SPACE 框架**由 Dr. Sarah Chen 开发，是 Vibe Coding 社区最广泛采用的 PRD 结构化方法，包含 5 个维度：

| 字母 | 维度 | 核心问题 |
|------|------|----------|
| **S** | Scope & Vision | 我要做什么？为什么做？ |
| **P** | People & Problem | 谁用？解决什么问题？ |
| **A** | Architecture & Approach | 用什么技术？怎么实现？ |
| **C** | Criteria & Constraints | 怎么算成功？有哪些限制？ |
| **E** | Execution & Evolution | 分几个阶段？怎么迭代？ |

### 4.2 详细模板

```markdown
# 产品名称：XXX

## S - Scope & Vision（范围与愿景）

### 一句话愿景
[用一句话描述应用的本质，比如："一个帮助用户记录每日饮食的轻量级工具"]

### 问题陈述
[描述用户面临的具体痛点，比如："上班族每天不知道吃什么，外卖吃腻了，自己做又嫌麻烦"]

### 成功定义
[明确衡量成功的标准，比如："用户能在 3 分钟内完成一餐的记录"]

### 边界设定
[明确应用不会做什么，比如："不提供食谱推荐、不支持购物清单、不做社交功能"]

---

## P - People & Problem（用户与问题）

### 用户画像
- **角色**：[比如：25-35岁上班族，单身或双职工家庭]
- **行为特征**：[比如：每天在外卖和食堂之间选择，偶尔自己做饭]
- **痛点**：[比如：想吃得健康但没时间/不知道怎么做]
- **使用频率**：[比如：每天1-3次]

### 使用场景
- **主要场景**：记录早午晚餐摄入
- **次要场景**：查看历史饮食记录
- **边缘场景**：修改历史记录、导出数据

### 用户访谈验证
[在正式开发前，访谈 3-5 位符合画像的真实用户，确认他们真的有这个需求——这是很多项目失败的第一步]

---

## A - Architecture & Approach（架构与技术）

### 技术选型
- **前端**：[如：Next.js 14 + shadcn/ui]
- **后端**：[如：Next.js API Routes / Express]
- **数据库**：[如：PostgreSQL + Prisma]
- **部署**：[如：Vercel / Railway]

### 技术约束
- 无状态设计（支持水平扩展）
- 所有接口必须进行身份认证
- 密码使用 bcrypt 加密存储

### AI 工具策略
- 使用 Claude Code 处理后端逻辑
- 使用 Cursor 处理前端组件
- 重要决策由人工确认

---

## C - Criteria & Constraints（标准与约束）

### 功能验收标准
1. 用户可以注册和登录
2. 用户可以记录每日三餐（早餐/午餐/晚餐）
3. 每条记录包含：食物名称、热量估算、进食时间
4. 用户可以查看历史记录（按日期筛选）
5. 数据存储在 PostgreSQL 中

### 非功能要求
- **性能**：API 响应时间 P99 < 200ms
- **可用性**：系统可用性 99.5%
- **安全**：所有接口 JWT 认证，密码 bcrypt 加密
- **兼容性**：支持 Chrome、Firefox、Safari 最近 2 个版本

### 资源约束
- 开发时间：2 周
- 预算：使用免费/开源工具
- 团队：1 人独立开发

---

## E - Execution & Evolution（执行与迭代）

### 分阶段开发计划

**Phase 0（第 1-3 天）**
- 用户注册/登录（邮箱+密码）
- 数据库模型搭建
- MVP 部署上线

**Phase 1（第 4-7 天）**
- 饮食记录功能（CRUD）
- 历史记录查看
- Phase 0 的用户测试与反馈收集

**Phase 2（第 8-11 天）**
- 数据可视化（周/月统计图表）
- 数据导出功能
- PRD 迭代更新

**Phase 3（第 12-14 天）**
- 移动端适配
- 性能优化
- 正式发布

### 测试策略
- 单元测试覆盖率 > 70%
- 关键路径自动化 E2E 测试
- 上线前人工 QA

### 迭代计划
- 发布后每周收集用户反馈
- 根据数据调整优先级
- 每个 Sprint 迭代一次

## 附录：输入输出示例

### 示例：POST /api/meals
```json
请求：
{
  "type": "breakfast",
  "food": "豆浆 + 油条",
  "calories": 450,
  "time": "2026-05-17T08:00:00Z"
}

成功响应（201）：
{
  "id": "meal_abc123",
  "type": "breakfast",
  "food": "豆浆 + 油条",
  "calories": 450,
  "time": "2026-05-17T08:00:00Z",
  "createdAt": "2026-05-17T10:00:00Z"
}
```

### 边界与异常
- 食物名称为空 → 返回 400 错误
- 热量为负数 → 返回 400 错误
- 未登录用户 → 返回 401 错误
- 一天记录超过 10 条 → 返回警告但不阻止
```

### 4.3 AI 友好写作的五项原则

| 原则 | 说明 | 错误写法 | 正确写法 |
|------|------|----------|----------|
| **结构化表达** | 分层描述，从抽象到具体 | 一大段文字描述 | 分章节、分点 |
| **避免模糊语言** | 用具体数字替代模糊词 | "提高性能" | "P99 < 100ms" |
| **尽量显式** | 不要隐含任何信息 | "系统需要安全" | "所有接口必须 JWT 认证" |
| **提供示例** | 示例是最强的"模式教导" | 只描述逻辑 | 提供 JSON 请求/响应示例 |
| **把决策写出来** | 解释为什么这样选 | 不写原因 | "不用 OAuth 是因为当前系统是内部系统" |

## 5. 工具生态全景

### 5.1 工具选型矩阵

| 工具 | 类型 | 最适合的场景 | 上手难度 |
|------|------|-------------|----------|
| **Claude Code** | CLI + Agent | 多文件重构、复杂 Bug 追踪、项目级理解 | 中 |
| **Cursor** | AI 增强 IDE（VS Code 衍生） | 日常补全、行级建议、快速迭代 | 低 |
| **GitHub Copilot** | IDE 插件 | 实时代码补全、简单任务 | 低 |
| **OpenClaw** | 多 Agent 框架 | 复杂任务拆分、CI 集成、并行开发 | 高 |
| **Windsurf Cascade** | Agent 自主执行 | 大型项目重构、复杂工作流 | 中 |
| **Replit Agent** | 云端 Agent | 快速原型、一键部署 | 低 |
| ** Lovable** | SaaS 平台 | 非开发者快速构建全栈应用 | 低 |

### 5.2 推荐组合

| 场景 | 推荐工具组合 |
|------|-------------|
| 日常业务功能开发 | Cursor 补全 + Claude Code 处理复杂逻辑 |
| 大型重构 / 架构调整 | Claude Code（Opus 4.6） |
| 独立开发 / 快速原型 | Claude Code（核心架构需自己想清楚） |
| 团队协作 / CI 集成 | OpenClaw Agent 工作流接入 CI/CD |
| 非开发者快速出 MVP | Lovable / Replit Agent |

### 5.3 Claude Code 核心命令

| 命令 | 作用 |
|------|------|
| `/init` | 初始化项目，生成规则文件引导大模型 |
| `/clear` | 重置对话上下文（适用于纠正超过 2 次仍不理想时） |
| `/best` | 重新生成最佳回复 |
| `/compact` | 压缩上下文，保留关键信息 |
| `/review` | AI 自动 Code Review |

### 5.4 国内用户配置 Claude Code

国内用户需要解决网络连通性和 Rate Limit 两大问题，推荐使用 API 中转服务：

```bash
# 在 ~/.zshrc 或 ~/.bashrc 中配置
export ANTHROPIC_BASE_URL=https://api.ofox.ai/anthropic
export ANTHROPIC_AUTH_TOKEN=你的_API_KEY

# 然后安装 Claude Code
npm install -g @anthropic-ai/claude-code
```

### 5.5 模型选择指南

| 模型 | 使用场景 | 特点 |
|------|----------|------|

## 6. 提示工程高级技巧

### 6.1 五项核心技巧

#### 技巧一：XML 结构化分隔

当 Prompt 包含多个部分时，用 XML 标签分隔，帮助 AI 区分不同内容：

```
背景信息：
[项目背景描述...]

任务：
[具体要求...]

格式要求：
[输出格式...]

示例：
[参考示例...]
```

#### 技巧二：Chain of Thought（思维链）

对复杂逻辑问题，显式要求 AI 展示推理过程：

> "请不要直接给出答案。先逐步列出你的思考过程，最后再给出结论。"

#### 技巧三：角色设定（System Prompt）

在对话开始时定义 AI 的角色和风格：

> "你是一位资深 Go 工程师，擅长高性能后端系统开发，代码风格严谨，所有函数必须有完整的错误处理。"

#### 技巧四：Few-Shot 示例

提供 1-2 个完整的参考示例，AI 对"模式"极其敏感，有例子时准确率显著提升：

```
提取关键信息并输出 JSON 格式，参考以下示例：

示例：
输入："张三的邮箱是 zhangsan@example.com，电话是 13800138000"
输出：
{
  "name": "张三",
  "email": "zhangsan@example.com",
  "phone": "13800138000"
}

现在处理以下输入：
[你的实际输入...]
```

#### 技巧五：任务链（Agentic Workflow）

将复杂任务拆解为多个顺序步骤，每个步骤的输出作为下一步的输入：

```
步骤 1（提取数据）：
"从以下报告中提取所有财务指标，输出 Markdown 表格格式"

步骤 2（分析数据）：
"基于上方表格，计算同比增长率和利润率，分析趋势"

步骤 3（生成摘要）：
"基于综合分析，写一份面向 CEO 的 200 字摘要，重点说明公司优势和潜在风险"
```

### 6.2 长文本处理技巧

| 技巧 | 说明 |
|------|------|
| **指令放在末尾** | 模型对开头和末尾最敏感 |
| **先问后文** | 先构建问题框架，再插入长文档 |
| **使用引导性问题** | 不要只说"总结"，要问具体问题 |

### 6.3 Vibe Coding Prompt 最佳实践

| 维度 | 正确做法 | 错误做法 |
|------|----------|----------|
| **上下文** | 包含技术栈、框架、代码规范 | 只说"帮我写个 XX 功能" |
| **参照物** | "参考 `src/utils/helper.ts` 的风格" | 不提供任何参照 |
| **症状描述** | "在数据量超过 10000 条时性能下降" | "性能有点差" |
| **验收标准** | "需要能处理 10k QPS" | "尽量优化一下" |
| **边界条件** | "用户名为空时返回 400" | "做好容错" |

## 7. 项目上下文管理

### 7.1 CLAUDE.md 最佳实践

`CLAUDE.md` 是 Claude Code 的项目级上下文文件，每次启动对话时 AI 会自动加载。

**内容应包含：**

```markdown
# 项目背景
[项目名称、功能定位、目标用户]

# 技术栈
- 前端：Next.js 14 + shadcn/ui
- 后端：Node.js + Express
- 数据库：PostgreSQL + Prisma ORM
- 部署：Vercel

# 代码规范
- 使用 TypeScript strict 模式
- 所有 API 响应使用统一格式：{ success, data, error }
- 错误处理遵循 `src/middleware/errorHandler.js` 的风格

# 架构决策
- 使用 App Router 而非 Pages Router
- API 路由在 `src/app/api/` 下
- 组件在 `src/components/` 下，按功能分组

# 特殊约束
- 不使用 Tailwind CSS（项目已自定义样式系统）
- 敏感配置通过环境变量读取
```

**核心原则**：越短越好，不写 AI 能从代码中直接读出的内容。

### 7.2 Memory Bank 系统

在项目根目录建立 `memory-bank/` 文件夹，包含以下文件：

| 文件 | 用途 |
|------|------|
| `game-design-document.md` | 原始设计文档（PRD/GDD） |
| `tech-stack.md` | 技术栈文档 |
| `implementation-plan.md` | 实施计划 |
| `progress.md` | 记录已完成步骤 |
| `architecture.md` | 各文件作用说明 |

**Always 规则配置示例（写在 CLAUDE.md 中）：**

```markdown
# Always Rules
- 写任何代码前，必须完整阅读 CLAUDE.md 和 memory-bank/ 下所有文件
- 禁止创建单体巨文件，每个模块文件不超过 300 行
- 所有新文件必须包含 JSDoc 注释
- 提交代码前必须运行测试
```

### 7.3 上下文管理六大策略

| 策略 | 说明 |
|------|------|
| **AI 写入上下文** | 让 AI 把关键决策和约定写入 CLAUDE.md |
| **决策推理可见** | 让 AI 在回复中说明"为什么这样设计" |
| **上下文垃圾回收** | 对话超过 50 轮后，整理压缩上下文 |
| **避免两个极端** | 既不过于频繁切换话题，也不过于冗长 |
| **管道化** | 后续问题建立在前面已知信息的基础上 |
| **可见性原则** | 保持上下文对双方都是清晰透明的 |

> **关键数据**：70 个需求之后 AI 注意力开始耗尽；处理 60 个文件 vs 10 个文件，发现 bug 的难度增加 75%。

## 8. 高级技巧与多 Agent 模式

### 8.1 Agentic Engineering 三原则

| 原则 | 说明 |
|------|------|
| **意图驱动** | 明确设定目标，而不是详细规定步骤 |
| **异步协作** | 接受 AI 自主规划，中间结果可审计 |
| **信任但验证** | 给 AI 自主权，但保留人工审查环节 |

### 8.2 OpenClaw 多 Agent 框架

当任务复杂度提升时，引入多 Agent 并行工作模式：

**OpenClaw 四大核心能力：**

| 能力 | 说明 |
|------|------|
| **动态分身** | 将复杂任务拆分为多个子任务，分配给不同 Agent |
| **异构模型协作** | 不同 Agent 使用不同模型（Opus 处理架构、Sonnet 处理实现） |
| **实时监控** | 可视化查看各 Agent 工作进展 |
| **结果聚合** | 合并多个 Agent 的输出，形成最终交付物 |

**任务拆解原则：**
- 控制在 3-5 个 Agent 以内
- 确保每个子任务相互独立
- 明确 Agent 之间的接口约定

### 8.3 Claude Code 内置 Agent 体系

| Agent 类型 | 使用场景 |
|------------|----------|
| **Plan Agent** | 复杂任务规划，生成详细的执行计划 |
| **自定义 Agent** | 针对特定领域（测试、安全审查等）配置专用 Agent |
| **Subagent** | 在主对话中调用子 Agent 处理子任务 |

### 8.4 Spec-Driven Development（规格驱动开发）

与 PRD 优先互补的方法：**先让 AI 跑出代码，再反推规格文档**。适合：
- 快速验证想法
- 不确定最优实现方式时
- 学习新框架时

## 9. 常见误区与避坑指南

### 9.1 七大翻车现场

| 误区 | 表现 | 正确做法 |
|------|------|----------|
| **并发状态混乱** | AI 生成看似正确的并发代码但实际有竞态条件 | 避免 AI 生成锁机制，人工审查并发逻辑 |
| **错误处理不完整** | 只处理正常路径，忽略各种异常 | 在 PRD 中明确列出所有异常场景 |
| **安全漏洞** | SQL 注入、XSS、敏感信息泄露 | 人工重点审查安全相关代码 |
| **隐式状态** | AI 假设某个全局状态存在但实际不存在 | 在上下文中明确说明状态来源 |
| **依赖地狱** | AI 引入未声明的依赖或版本冲突 | 指定具体版本号，人工验收依赖清单 |
| **伪测试** | AI 生成"永远通过"的测试 | 测试用例必须由人设计边界条件 |
| **不理解就 Debug** | 直接问 AI 答案而不理解代码逻辑 | 先读懂代码，再让 AI 解释 |

### 9.2 六大致命错误

| 错误 | 说明 |
|------|------|
| **把 AI 当搜索引擎用** | 零散提问而非完整描述任务背景 |
| **不 Review 直接提交** | 必须审查关键逻辑再合并代码 |
| **每次从零开始** | 不维护上下文，导致每次都重复解释 |
| **完全依赖 AI 做决策** | AI 负责执行，方向判断必须由人做 |
| **过度迭代** | 同一问题纠正超过 2-3 次仍不理想时，应该 `/clear` |
| **跳过测试** | 一定要跑通测试再提交，不要"看起来对就行" |

## 13. 总结与行动建议

### 13.1 核心要点回顾

1. **Vibe Coding 是方法论，不是工具集**——它代表的是一种全新的编程思维方式
2. **PRD 文档是第一步**，不是可选项——有它项目完成率 85%，没它只有 22%
3. **人与 AI 的分工**：你负责想清楚方向，AI 负责执行实现
4. **迭代反馈循环是精髓**——生成 → 运行 → 反馈 → 修改，循环直至满足
5. **人工 Code Review 不可跳过**——AI 代码必须经过人审查才能合入
6. **Context Engineering 是工程化关键**——CLAUDE.md 和 Memory Bank 让 AI 持续保持理解
